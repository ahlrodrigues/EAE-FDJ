Objetivo

Atualização de rumo (2026-04-11)

Atualização de rumo (2026-04-13)
-------------------------------
Decisão: manter o sync de conteúdo do app como “manifest + itens” (fluxo
dirigente → alunos, liberado pela data da atividade no programa), e introduzir
um segundo canal para “troca de pacotes” (requests/packages) quando houver
necessidade de retorno aluno → dirigente (somente sob solicitação).

Arquitetura alvo (pacotes):
- API mínima: autenticar, autorizar, listar pendências, registrar status,
  emitir URLs (upload/download), expiração e limpeza
- Object storage: guardar apenas blobs (criptografados) temporariamente
- App local: montar pacote incremental, criptografar/assinar, enviar, baixar,
  validar, aplicar e confirmar

7) API DO SITE (MÍNIMA) — OTP + PULL INICIAL
--------------------------------------------
Endpoints sugeridos:
- POST `/api/enroll/request-otp`
  Entrada: `{ turmaCode, email }`
  Saída: `{ ok: true }` (resposta sempre genérica para evitar enumeração)
  Ação: se e-mail estiver pré-cadastrado na turma, enviar OTP por e-mail.

- POST `/api/enroll/verify-otp`
  Entrada: `{ turmaCode, email, otp }`
  Saída: `{ ok: true, turmaConfig }` (apenas whitelist)
  Ação: valida OTP (hash + TTL + 1 uso) e retorna config.

Requisitos de segurança:
- Normalizar e-mail: `trim().toLowerCase()`
- Armazenar e comparar aluno por `sha256(email_normalizado)` (evita guardar e-mail em claro)
- OTP armazenado como hash (não em claro), TTL curto (ex.: 10 min), invalidar após uso
- Rate-limit por IP + por turmaCode + por hashEmail
- Logs de auditoria (geração de OTP, validações, falhas)

10) SYNC DE PACOTES (REQUESTS + PACKAGES) — ALUNO → DIRIGENTE (SOB DEMANDA)
==========================================================================
Meta: permitir que o dirigente publique uma SOLICITAÇÃO (request) e o app do
aluno responda enviando um pacote incremental para o dirigente.

Regras de autorização (evita “bidirecional aberto”):
- Conteúdo: dirigente → alunos (publish de materiais)
- Respostas: aluno → dirigente apenas se houver `requestId` aberta e válida

Endpoints mínimos sugeridos (API):
- POST `/api/requests` (dirigente cria solicitação)
- GET  `/api/requests?to=<alunoId>&status=open&available=1`
- POST `/api/packages` → retorna `packageId` + `uploadUrl`
- PUT  (uploadUrl) → envia blob do pacote
- GET  `/api/packages?to=<dirigenteId>&status=pending&available=1`
- GET  `/api/packages/:id/blob`
- POST `/api/packages/:id/downloaded`
- POST `/api/packages/:id/applied` (confirmação + limpeza)

Status mínimos:
- request: `open|closed|expired`
- package: `pending|downloaded|applied|failed|expired|deleted`

DEV (hoje):
- `tools/mock-api/server.js` simula `requests/packages` e guarda blobs em disco
  (`tools/mock-api/_storage/`).
- App: IPC expõe `window.api.requests`, `window.api.packages`, `window.api.responses`
  para teste e evolução (criptografia fica para próxima etapa).
- Dirigente gera `turmaCode` e compartilha com a turma (pode ser texto/QR)

13) WEBSOCKET (PUSH) PARA “UPDATE AVAILABLE”
--------------------------------------------
Meta: avisar o app quando houver atualização, sem baixar conteúdo automaticamente.

Servidor WS:
- Autenticação: token curto gerado no enroll (OTP) e renovável
- Canal por turma: `turma:<turmaId>`
- Evento: `updateAvailable`
  Payload: `{ turmaId, manifestVersion, updatedAtISO, summary? }`

Cliente (Electron renderer ou main):
- Conectar no login/index (somente quando sessão ativa)
- Reconnect com backoff
- Ao receber `updateAvailable`, exibir banner/badge “Há atualizações”
- Botão “Atualizar” chama o fluxo HTTP (step 12) e persiste localmente

Fallback:
- Se WS falhar, o app pode rodar `checkUpdates` via HTTP ao abrir (polling leve).
